# Hub Connect — design v1 implementation plan, revision 4

Status: planned work, not an implemented or tested release. The revision-4 brief and the owner's 1/11 repository split supersede the previous plan wherever they differ.
This planning change writes only `docs/PLAN.md`; every other path below is a future implementation deliverable.

## 1. Goal, non-goals, and success criteria

A Player discovers an open Land, proves possession of their key to that Land, passes its door rules, and plays while the Map server sits behind a home modem.
The Hub is a free, neutral directory and ciphertext relay, run by operators from the PRIVATE `linked-realms-hub` repository; self-hosting instructions are for authorized operators. It is only a connection service and is never trusted with Player/Land keys. Entering is free. Only the Land admits Players. The root-seed-holding agent runs on strangers' machines and MUST be open source and rebuildable, never a closed binary (owner decision 1/11).
Independent Hubs share no database, synchronization, or links. Replacing transport/discovery with a mesh must not change game code or admission messages.
Identity is ONE global Ed25519 key per Player (derived from the Player's root seed, section 4), generated by the player-mode agent and used on every Land; no account, wallet requirement, external identity provider, or verification service for Hub Connect. Parallel Game work removes old EVM authority and adds profiles/local state; the separate Chain track owns game gold and mining.
Public cards/control metadata are visible; game content, proofs, invite secrets, matchmaking and game frames are encrypted between player-mode agent and Land.

Hub Connect release milestone: **10 Lands for seven consecutive 24-hour UTC periods**, each connected to two independent Hubs.
Use two test Players/Land with separate keys (one continuously connected gameplay Player A; probe Player B makes one fresh entry probe/Land every five minutes), so probes never close the gameplay session (one-active-session rule, section 6). Player A resumes with a fresh entry after injected failures or UI reauthentication (section 9); these interruptions remain in the evidence, not excluded uptime.
Each Land: >=99.5% daily probe availability; >=99% eligible entry success; entry p95 <=5 s; encrypted RTT p95 <=500 ms on measured network RTT <=100 ms.
Daily kill/blackhole exercises recover within 45 s; Hub restart exercises rebuild only cards and tunnels within 45 s of connectivity returning; Hubs hold no invite state.
Zero unauthorized entries, repeated code redemption, plaintext relay leaks, lost committed invite records, or unbounded queue growth.
Section 13 defines computation, coverage and resource thresholds. Missing evidence fails; a failed day restarts the seven-day window.
Quest implementation begins only after this milestone; phase-1 quest counter stays zero.

Excluded from Hub Connect: fees, tickets, payment proofs, chain RPC, gold, mining, NFTs, external wallets, SIWE, wallet bindings, identity verification, NAT hole-punching, Hub-to-Hub links, global chat, world-data caching, paid Hub tiers, scheduled key rotation, per-frame signing, large-scale load testing, Hub mailbox/inbox, and credit-based flow control.
Hub, cards, entry and relay never carry chain traffic (RPC, transactions, balances, mining) and no plaintext or public metadata a Hub can read contains a wallet address; the only address on the wire is the optional `wallet` field inside the end-to-end encrypted GREETING (section 4); chain/mining traffic goes directly from the player agent to the chain network, never over a Hub tunnel.
The game has its own new RandomX PoW chain from day one, merge-mined with Monero for "free-ride" mining on Monero work; its node, agent-held wallet and agent miner belong to the parallel Chain track (C0–C6). G1 removes the old EVM chain, contracts, SIWE and NFT characters from the connect build; the new game chain is a separate system, and it launches on a TESTNET first (owner decision; mainnet only later through its own gate, section 19).
Colyseus SDK patching is excluded unless S0 demonstrates the loopback approach impossible; section 9 defines the conditional fallback.
Player-signed name/image follows the key via optional GREETING profile. Stats and inventory remain per-Land, per-key in SQLite; another Land starts from its defaults. Gold lives on the game chain, belongs to the player's wallet key (derived from the same root seed as the identity key, section 4) held by the player-mode agent, and travels across all Lands.

## 2. Architecture and state ownership

```text
Player machine                  Independent Hubs              Land machine behind NAT
browser + unpatched SDK         +----------------+            connect-agent land
  | loopback HTTP/WS            | Hub A: RAM only |<-- WSS ----  | identity + Noise + routes
connect-agent player -- WSS ---->| cards/tunnels   |             | transient admission
  | key + Noise + embedded UI   +----------------+             | authenticated local API
  +----------------- WSS ------>| Hub B: RAM only |<-- WSS ----  v
                                +----------------+            game Node: land.db + doors
player agent <================ end-to-end Noise ============> land agent
                                                               | fixed loopback HTTP/WS
                                                              Node Colyseus + LandRoom/world
```

One Hub origin identifies one Go process: TLS termination allowed, random RAM-instance balancing forbidden. Each Land runs one agent (all Hub connections) and one game Node/Colyseus room (durable decisions).
`cmd/hub` lives only in PRIVATE `linked-realms-hub`; `cmd/connect-agent` lives in NEW PUBLIC `linked-realms-connect` (placeholder name, owner may rename). The public repo owns an independently importable Go module at `protocol-go/` for codecs/envelopes/signatures/errors/replay rules, replacing the proposed shared `internal/protocol`: cross-repo imports cannot target a Go `internal/` package. Both binaries import this one implementation; the Hub pins its exact version in `go.mod` with module/content hashes in `go.sum`, never copies codecs. Only the public agent imports `internal/noisesession`; private Hub CI proves `go list -deps ./cmd/hub` excludes `github.com/flynn/noise` and runs public vectors against the pinned protocol module. Production Hub has no Noise endpoint, agent key-management code or Player/Land session secrets. Section 11 defines repository ownership and publication gates.
TypeScript has no Noise/X25519/ChaCha/handshake/session code; browser gets no private keys. Trusted UI is agent-embedded, never Hub-supplied.

| Owner | Persistent state | RAM state / restart behavior |
| --- | --- | --- |
| Hub | Provisioned deployment config and own identity/pins only; re-deployable inputs, no database or invite state | Cards, tunnels, routes, nonces, rate buckets, quests; all disappear |
| Land: agent + Node | Agent-only root-seed file (identity + C4 reward wallet), restore epoch/high-water sidecar, reward caps/reservations/idempotency/authorizations; Node-only land.db: policy/revision, card counter, codes, members, bans, signed profiles/revisions, per-key stats/inventory; game/world | Agent: fresh X25519 key/boot ID, challenges/seats/sessions/nonces; Node: generation/capability/reservation state keyed by session ID; restart fencing in section 9 |
| Player: agent + browser | Agent: root seed (global identity + derived chain wallet key, C2), signed profile/revision, access token, Hub preferences, card high-water marks, Land-key contacts, pending invite codes; browser: UI preferences only | Agent: Noise sessions/bridge handles/bootstrap tokens; browser: UI capability/room/display data; restart requires fresh entry |
| Game chain (C1) | Gold accounts/balances and transfers, owned by wallet keys; testnet first (mainnet gated later) | Node synchronization/reorg recovery; never Hub state |

Hub logging has no content; keys, IPs, sizes and timing remain observable metadata, not anonymity guarantees.
An operator scraper may retain numeric aggregates outside Hubs without coordinating their operation.

### Key neighbors and contracts

`linked-realms-connect` (public) owns the wire/local-API specifications, vectors, public Go protocol module, TS codecs, agent and its release manifest. `linked-realms` (public game) keeps `packages/connect-node`, client source/build and game state; it consumes the pinned public TS package and local-API contract. `linked-realms-hub` (private operator service) consumes the pinned public Go module and vectors, and owns the connection-service implementation and operator deployment policy. The shared contracts are signed wire objects, opaque relay frames and the versioned agent <-> Node local API, not shared private source or copied codecs. Key-neighbor adjacency remains the game-owned schema in section 10; it grants no authority. Public source/build dependencies never point to the private Hub repo; private integration CI may consume public artifacts.

## 3. Wire protocol

`protocol/v1.md` in public `linked-realms-connect` is normative; its `protocol/vectors/v1.json` contains inputs, exact bytes and rejection results. Unqualified `protocol/`, `tools/vectorgen`, `tools/checkspec`, `protocol-go/` and agent paths below refer to that public repo after T01m; Hub paths refer to the private repo and game paths to `linked-realms`. These are planned destinations, not claims that files have moved in this edit.
`protocol/manifest.json` locks exactly the SHA-256 of `v1.md` and `vectors/v1.json` at T01 using spec-level checks. T02 adds the separately pinned `vectors/nk-transcript.json` entry without changing either original hash; release readiness requires T02 production crypto/parity CI. T01m migrates the existing T01 artifacts unchanged before T02. Hub and game checkouts pin the public protocol release and manifest hash; the game also locks the public TS package version/integrity. Client build pins live in the public repo's per-release `protocol/agent-release.json` (section 9), never in the private Hub repo.
Unsigned integers are big-endian; `u64` uses TS `bigint`. Keys/hashes are 32 bytes, IDs 16 bytes, signatures 64 bytes.
`blob`/`text` = `u32 length || bytes`; text is strict UTF-8, no normalization. Lists use `u16 count`; optional fields use 0/1 byte.
Reject trailing bytes, invalid UTF-8/booleans, unknown kinds, oversized fields and noncanonical encodings before large allocation.
Diagnostic JSON uses decimal strings for `u64`, lowercase hex keys and unpadded base64url blobs; JSON is never signed.

### Signed control envelope

| Field in order | Encoding / meaning |
| --- | --- |
| `magic`, `version`, `kind` | ASCII `LRC1`, `u16=1`, `u16` message code |
| `sender`, `recipient` | Ed25519 keys; zero recipient only for published objects and initial Hub challenge |
| `context` | ID: Hub boot for HTTP controls, connection ID for tunnel controls, Noise session ID for encrypted controls; zero for objects/bootstrap |
| `nonce` | Fresh random 32-byte single-use control nonce |
| `issued_at`, `expires_at` | Unix seconds, `u64` |
| `body_length`, `body`, `signature` | `u32`, exact body bytes, Ed25519 signature |

Header 140 bytes; total overhead 204 bytes. Sign `ASCII("linked-realms/connect/control/v1\0") || header || body`.
Kinds distinguish signed objects from executable requests. Reading a stored card is not execution of its original nonce.
Identical-object publication is idempotent; every registration/query/update wrapper has a new nonce.
Every Hub reply prefixes body with `request_hash:bytes32, hub_time:u64, hub_boot:bytes16`; unsolicited reply uses zero request hash.
Replies are Hub-signed/recipient-bound; acknowledgements/errors identify request hash and confer no Land admission authority.
Verification checks expected sender, recipient, context and state, not merely a valid signature; encrypted controls must name the route's Player/Land and exact Noise session.

### Message catalogue

Fields are in serialization order; common Hub reply prefixes omitted. `sid` = Noise session ID; `route` = Hub-local random ID.
`endpoint` = `(origin:text<=192 bytes, hub_key:bytes32)`; canonical HTTPS origin, no credentials/path/query/fragment.
`reason` is `u16`; revision/time fields `u64`; counts/lengths `u32` unless specified.

| Code / kind | Body and location |
| --- | --- |
| 1 `INFO_REQUEST`; 2 `INFO` | Empty request; reply `origin, versions:list<u16>=[1], max_frame, max_card, max_routes_per_land, max_streams`; HTTPS bootstrap |
| 3 `DIRECTORY_QUERY`; 4 `DIRECTORY_PAGE` | `land:optional<key>, cursor:optional<key>, limit:u16<=64`; exact Land key lookup or public listing; reply `next:optional<key>, entries:list<(card:blob, online:u8, observed_at)>`; `online` is this Hub's signed live-tunnel observation at `observed_at` (section 5), never card-derived |
| 5 `REGISTER`; 6 `REGISTERED`; 7 `CARD` | `card:blob`; reply `card_hash, revision`; CARD in section 5; authenticated Land tunnel |
| 8 `ACK` | Reply `operation:u16,revision`; heartbeat and close acknowledgement |

| 13 `ROUTE_OPEN`; 14 `ROUTE_OFFER`; 15 `ROUTE_READY` | Player: `land,sid,card_hash`; Hub to Land: `route,player,sid,card_hash,peer_ip:text<=45`; reply to Player: `route,sid` |

| 32 `QUEST_RESULT` | Phase 2 encrypted posting-Land-signed `accept_hash,quest_id,status:u8,fulfillment_id:id`; status 0 rejected, 1 accepted, 2 paid |

Before v1 is locked, freeze both message-kind and encrypted-operation tables in `protocol/v1.md` contiguous from 1. Thereafter numbers are never reused or reassigned; additions take the next unused number or bump the protocol version. Reject unknown codes as unknown kinds.

HTTP: `POST /v1/info`, `/v1/directory/query`, phase-2 `/v1/quests/{query,post,remove}`; `application/octet-stream`, one envelope/body.
HTTP request cap 8 KiB, reply cap 512 KiB; <=64 cards/page; no invite enumeration endpoint.
WSS: `/v1/tunnel/<land-key>`, `/v1/connect/<land-key>`; subprotocol `linked-realms.v1`; path keys 64 lowercase hex.
Registration/card updates require tunnel's authenticated Land; route controls require authenticated route owner or Hub/Land endpoint.
ROUTE_OFFER is notification, not door decision: Hub checks signature/live tunnel/current unexpired card/limits, creates route, notifies both endpoints.
Land can close overload/invalid routes immediately. Route creation never reserves a Colyseus seat. On ROUTE_OFFER, reserve pending capacity before allocation/DH; a fixed 10 s monotonic deadline covers NK through a verified GREETING, never extended by traffic, heartbeat or reroute. A reroute is a new quota/rate-limited attempt, not a reset of the old one. Timeout closes the route and releases all pending resources.

`signed_profile = player_key:bytes32, revision:u64, display_name:text<=32 UTF-8 bytes, avatar_kind:u8, avatar:blob, signature:bytes64`; no expiry. Sign `ASCII("linked-realms/connect/profile/v1\0") || canonical preceding fields`; key matches GREETING sender, agent persists increasing revision before signing.
Avatar kind 0 = allowlisted preset ID (<=32 ASCII bytes); kind 1 = `mime:u8` (0 PNG, 1 JPEG, 2 WebP) + image bytes <=8 KiB, <=128x128 pixels; no SVG/HTML/remote URLs. Whole profile <=9 KiB.
Land verifies signature/bounds, stores highest revision and signed bytes per key; lower revisions rejected, equal revision accepts identical bytes only. Admission commits profile only for an eligible key.
Land relays original SIGNED profiles; clients verify key/signature/revision, reject rollback/conflicts and treat all display data as untrusted: size-check/escape text, validate image format/dimensions, decode only through safe browser `img` with local blobs/presets, never HTML. Land cannot forge name/image; omitted profile uses stored profile or key/default preset.

### Unsigned data frames and encrypted multiplexing

WS discriminator: `0=control envelope`, `1=Noise handshake`, `2=Noise transport`; every WS record including discriminator <=32 KiB.
Transport header: `type:u8=2,version:u16=1,route:16 bytes,sequence:u64,length:u32`; then ciphertext, no signature.
Header is 31 bytes, authenticated as Noise AEAD associated data. Ciphertext cap 32,737 bytes includes 16-byte tag.
Sequence starts zero per direction, equals Noise transport counter; accept exactly the next value.
Handshake uses same header with `type=1,sequence=0`, then `card_hash:32 bytes || Noise_message:blob`; payload <=4 KiB.
Both handshake messages have empty application payloads. Signed GREETING/CHALLENGE/PROOF run after NK completes.
Hub forwards opaque records by route/socket ownership; never verifies/decrypts/signs game frames.
Bad tag, repeated/skipped/reordered sequence, wrong route/version or counter exhaustion closes whole session; never drop ciphertext then continue.

Decrypted payload: `op:u16,stream:u32,body`; stream zero = control; Player-created odd stream IDs never reused.
Operations: 1 `SIGNED_CONTROL(envelope:blob)`; 2/3 `PING/PONG(random:bytes16)`; 4 `SESSION_CLOSE(reason)`.
5 `HTTP_START(method:text,path:text,headers:list<pair>,total:u32)`; 6 `HTTP_BODY(offset:u32,final:u8,bytes:blob)`.
7 `HTTP_RESPONSE(status:u16,headers,total)`; 8 `HTTP_RESPONSE_BODY(offset,final,bytes)`; 9 `WS_OPEN(path:text)`; 10 `WS_READY()`.
11 `WS_DATA(message_id:u32,binary:u8,offset:u32,total:u32,final:u8,bytes:blob)`; 12 `STREAM_CLOSE(reason)`.
Chunks <=16 KiB; exact contiguous offsets/final lengths. Empty bodies send final chunk. Close aborts I/O and frees buffers.
At most 8 streams/session, 2 concurrent HTTP, 1 game WS; HTTP request <=64 KiB, response <=512 KiB.
Each stream starts once, completes or closes once; operations before START/READY or after final/close fail. HTTP cannot turn into WS; IDs/counters cannot wrap.
WS messages <=16 KiB Player-to-Land, <=1 MiB Land-to-Player (existing 256 KiB validated map plus serialization).
Headers <=16 sorted unique lowercase pairs, <=4 KiB total, names <=64 bytes, values <=512, no CR/LF. Method <=8 ASCII bytes; path <=2 KiB.

### Time, replay, versions, and errors

Executable controls live <=60 s; authentication/challenges <=30 s. Skew 120 s: reject `issued_at>now+120` or `expires_at<now-120`.
Enforce issue<=expiry, lifetime limits and local monotonic deadlines; skew never lengthens a 30 s seat.
Keep `(sender,context,nonce)` until **at least expires_at+120 s**, and >=180 s after acceptance for 60 s controls.
Maximally future-dated accepted control needs up to 300 s retention from receipt; use monotonic removal deadlines against rollback.
Hub nonce cap 200,000; Land 20,000; reject new work when full, never evict live nonces. Record rejected authenticated mutations too.
Fresh Hub boot/connection challenges and Land boot/session/key prevent old requests after restart; HTTP mutations require current Hub boot.
Cards/links/quests use expiry and revision/lifecycle, not command nonce semantics. Cards/links close at effective expiry, no extra serving grace.
Every Hub reply includes time, even errors. Player agent estimates per-Hub offset from request midpoint, capped +/-120 s; never sets OS clock.
Hub time cannot extend local invite/challenge/seat/session deadlines; larger disagreement gives clock error and another Hub, not relaxed checks.
URL/subprotocol/envelope/frame/card/prologue versions must agree. One suite, no negotiation/downgrade; reject unknown version before body.

Errors (`u16`): 0 orderly close; 1 `MALFORMED`; 2 `UNSUPPORTED_VERSION`; 3 `BAD_SIGNATURE`; 4 `EXPIRED`; 5 `REPLAY`; 6 `POLICY_CHANGED`; 7 `ENTRY_DENIED`.
8 `STALE_CARD`; 9 `OFFLINE`; 10 `BUSY`; 11 `RATE_LIMITED`; 12 `STREAM_CLOSED`; 13 `TIMEOUT`; 14 `CLOCK_SKEW`; 15 `NOT_FOUND`; 16 `STORAGE_UNAVAILABLE`.
Hub errors mean transport/discovery only; encrypted Land denials generic. Internal numeric reasons distinguish bans/invites/capacity/storage.
Unauthenticated malformed traffic may drop silently; signed HTTP errors use 400/401/404/409/429/503; unsigned proxy errors are transport failures.
Go consumes all vectors: every envelope/kind/frame, frozen message kinds 1–32 and encrypted operations 1–12, sizes, strict signatures, full NK transcript, AD and replay/clock edges. TS consumes only card/link/profile bytes, hashes, signatures, revisions and bounds.

## 4. Identity, key file, and crypto

A Hub identity is a random Ed25519 seed from the OS CSPRNG on first run (a Hub has no wallet). A Player and a Land each have ONE 32-byte CSPRNG root seed (BIP39-compatible entropy: a later recovery-phrase UI only encodes the same 32 bytes as 24 words, no file-format change), generated on first run, so each owner has one seed; a Land recovery bundle also includes the durable state in section 7. Identities are public keys. Land agent generates fresh X25519 static key each agent start, publishes higher card revision; private Noise key stays in RAM.
Player and Land branches, all hardened, fixed derivation paths recorded in `protocol/v1.md` (T01) with test vectors: identity = Ed25519 via SLIP-0010; chain wallet = two frozen profiles with full paths and vectors in `v1.md` — profile A BIP32 secp256k1 (C1 forks a Bitcoin-style UTXO chain) and profile B a second SLIP-0010 Ed25519 branch (C1 builds an account-model chain); C1 only selects the profile, it never edits `v1.md`. Both master keys are computed from the 32 root bytes directly (no mnemonic-passphrase stretching), so the 24-word encoding of the same bytes reproduces both. Hardened derivation gives outsiders no public link between identity and wallet keys. Binding (decided: wallet address in the encrypted session, not an on-chain registration): the optional `wallet` field of the identity-signed GREETING (section 3) carries the Player's wallet address; the identity signature covers it, so the Land agent hands the verified address to the Node and the Node can pay rewards without any chain lookup. The Hub sees only ciphertext; chain isolation means no chain traffic over Hub tunnels, not that an address cannot sit inside an encrypted session. A claimed address needs no proof of wallet control: a wrong address only misdirects the claimant's own reward. Nothing else links the two keys; C2 and C5 use this same field. A Land's reward wallet is the Land's own wallet branch (same profile as the Player): the Land agent signs only fixed-type reward transfers the Node requests through the local API, bounded by two owner-set spend caps — per transaction and per UTC day — so a captured Node cannot drain the wallet with many small transfers. The cap state is a small agent-owned file in the Land agent data directory (never land.db): both caps count total wallet debit: reward amount plus all network/priority fees, using overflow-checked arithmetic. The agent estimates and reserves a fee ceiling plus amount atomically and fsyncs BEFORE signing/sending; reject if either cap cannot cover amount+fee. Every fee bump/replacement reserves any additional debit against the same reference and applicable UTC-day budget before signing; verify outputs/change and enforce the fee ceiling, releasing excess only after a definitive outcome; a corrupt/unreadable state, or a pending reservation of unknown outcome, fails closed (no spending) until the owner resolves it by CLI; the day key is the UTC date, and a wall clock that moves backwards keeps the latest day seen, so restart, rollover or clock rollback never re-grant a spent cap; wallet keys never reach land.db or the Node. C2 applies the same restricted-file/ACL, safe creation/locking and backup protections below; no local-API key export, fixed-type transaction signing only. Root-seed export/import happens only through explicit user CLI actions (`connect-agent key export/import`), never the local API. One leaked root seed leaks both identity and wallet. Land restore/import locks reward spending until section 7 reconciliation; importing an existing seed is never first-wallet initialization with zero spent budget.
Only `Noise_NK_25519_ChaChaPoly_SHA256`; prologue: `ASCII("linked-realms/connect/noise/v1\0") || u16(1) || player || land || sid || SHA256(signed_card)`.
PROOF signs completed handshake hash with Land challenge, binding identities/session/card before admission.
Retain current-boot signed cards until expiry for prologues; no old-boot private static keys. No sensitive payload before completed NK. Go uses stdlib Ed25519/SHA-256; `github.com/flynn/noise` is the sole Noise implementation, used only by the agent and test peers, restricted to `Noise_NK_25519_ChaChaPoly_SHA256`.
T02 records exact version/commit/hash and known review/audit evidence in `protocol/crypto-dependencies.md`; unknown stays unknown, no unsupported audit claims. Require standard suite and project transcript/AD/negative vectors (including invalid/all-zero DH); no handwritten handshake/assembled NK primitives.
TS: pinned `@noble/curves` strict Ed25519 (`zip215:false`) verification of cards/links/profiles for browser/Node, bounded encode/strict decode, agent local-API client only.
Fresh session before 2^20 records or 1 GiB/direction; never reuse nonce/key pairs, resume ciphertext or implement bespoke rekeying.
Clear ephemeral/session secrets as Go permits; erasure is not guaranteed. Endpoint compromise defeats E2E.
Key file `identity.json` <=2 KiB: `{format:"linked-realms-key",version:2,kind:"player"|"land"|"hub",algorithm:"Ed25519",public_key,seed,created_at,encryption:"none"}`. Version 2 is the frozen format (T01); the earlier draft version 1 (a single Ed25519 seed for every kind) is rejected. For `hub`, `seed` is the Ed25519 seed; for `player` and `land`, `seed` is the root seed and `public_key` is the SLIP-0010 identity-branch key (agent recomputes and verifies it; wallet keys are never stored separately).
Key/seed = canonical unpadded base64url, 32 bytes decoded; verify match; reject unknown fields/versions and permissive files.
Agent data: `%LOCALAPPDATA%\LinkedRealms\Connect` on Windows; `$XDG_DATA_HOME/linked-realms-connect` (default `~/.local/share/linked-realms-connect`) on Linux.
POSIX dirs/files 0700/0600; Windows disables inheritance and grants current user only; administrators remain OS trust boundary.
Create restrictively before write; reject symlink/reparse swaps, exclusive identity process lock, fsync before use; no silent overwrite.
**Passphrase encryption is not v1**; versioned `encryption` allows future format. Explain backup theft risk on export.
CLI `connect-agent key export <path>` / `connect-agent key import <path>`; restricted destination and fingerprint confirmation before replacement.
UI exposes instructions/status, never key bytes or arbitrary file API. Import stops sessions, validates, atomically replaces; invalid import leaves old key.
Only land agent reads Land identity, never Node/DB; back up the complete Land recovery bundle per section 7. Lost Player key requires new identity; recovery/device linking deferred.

## 5. Directory and cards

CARD body: `land_key,name:text<=64,description:text<=512,noise_key,door_mode:u8,hubs:list<endpoint>[1..8],current_players:u16,max_players:u16,protocol_version:u16=1,revision:u64,policy_revision:u64,allow_guest:u8=0`.
Envelope sender equals land_key, recipient/context zero; expiry is card expiry, `expires_at-issued_at=600 s`; whole signed card <=4 KiB.
Door 0 = public, 1 = invite-only; other modes invalid. Population advisory, `current<=max<=64` for this game release.
Hub list sorted/unique; no Map private IP, chain address or world data. Node commits strictly increasing card revision in land.db before requesting agent signing/publication.
Every 120 s and immediately on restart/policy/endpoint change, Node commits higher revision/current metadata FIRST; agent fills/signs a NEW card with fresh issued_at/expires_at, publishes identical bytes to all Hubs. Refresh requires higher revision.
Equal revision only accepts identical bytes; lower revision or equal/different bytes fail. Hub retains revision tombstones until card expiry+skew.
ROUTE_OPEN must name the current unexpired `card_hash`: card expiry blocks new routes, not tunnel openness; existing sessions continue under liveness and door policy. A live tunnel without an unexpired card is **connected but undiscoverable/not enterable**, a land-agent fault given the 120 s refresh; the Hub never serves an online entry without an unexpired card.
List/search only unexpired public cards; invite-only lookup must name the exact Land key, no cursor, at most one result; unknown/expired returns NOT_FOUND. Rate-limit per IP/key (section 13), no invite-only enumeration endpoint.
Land keys are 32-byte randomly generated Ed25519 identities, unguessable without disclosure; key leak = nonsecret card (name + population), never entry authority. Public-to-invite-only stops listing/search; cached copies are not secret by design.

## 6. Entry flow and admission ownership

1. Player agent validates card (invite-link lookup if needed), chooses advertised Hub, authenticates outbound WSS with signed fresh LINK_CHALLENGE response.
2. Player agent signs ROUTE_OPEN. Hub checks signature, live Land tunnel, unexpired card and limits; never bans/invites/door eligibility.
3. Player and land agents complete NK using card key/prologue; until admission only handshake and entry controls are accepted.
4. Player agent sends signed encrypted GREETING with `key_class=0` (same global agent key on every Land) and optional player-signed profile and optional `wallet` address (covered by the same signature); class 1 reserved guest, rejected in v1.
5. Land agent sends signed encrypted CHALLENGE: fresh random 32 bytes, boot, policy revision, 30 s monotonic deadline; store by `(player,sid)`.
6. Player agent sends signed encrypted PROOF over challenge and completed handshake hash; raw invite code sent here if membership must be established (then verified local handoff to Node).
7. Land agent verifies GREETING/PROOF signatures/session/boot/hash/deadline, atomically consumes challenge and sends verified record to Node. Node applies bans first, then public access or invite-only membership/durable redemption.
8. Node serializes redemption with policy/generation changes; commits code use and membership in one SQLite transaction before allow. Agent signs SEAT_GRANT or generic ENTRY_DENIED; disk failure means no grant.
9. Seat binds exact `(player,land,sid,boot,generation,policy_revision)` with one 30 s deadline covering reservation and WS join; never reset between stages.
10. Only accepted session can send matchmaking HTTP. Land agent injects Node-issued private one-use loopback capability; onAuth consumes, onJoin rechecks generation/policy/deadline.
11. New proven entry replaces old session for that key/Land; atomically fence old inputs before granting new generation. Challenges alone cannot evict.
12. Door/list changes cancel pending challenges/seats, increment policy revision, republish card, eject active keys no longer eligible. Ban beats owner status.

One land agent shares RAM across Hubs: atomic single-use challenges, nonces (section 3), seats/session fences; <=80 aggregate sessions. Node owns durable policy/redemption and generations/capabilities/reservations keyed by session ID. Pending routes count inside the 80 from offer receipt, with <=16 unauthenticated pending routes/Land and <=8 per authenticated Hub identity (including all its connections), held until valid PROOF or close; the existing challenge deadline applies after GREETING. Enforce on TCP+WSS alike; one Hub cannot exhaust the aggregate pending budget.
Pending challenges/seats <=160/80 per Land, <=2/1 per key; 64 joined seats. Monotonic timers and serialized decisions across local-API/disk work; no unprotected read-modify-write across await. Recheck policy/generation after I/O. Fail closed if committed disk state cannot reconcile with RAM.
Bind exact `(processId,roomId,sessionId)` from HTTP reservation; consume once on WS open. Direct loopback requests without capability cannot reserve seats. Fence delayed onJoin/onLeave/game callbacks; old callback cannot delete new session. Failed join never undoes committed code use.
Same invited key retries without a code, or with its used code idempotently after a lost reply; another key cannot reclaim consumed code. Player agent keeps the Land key as a contact for exact lookup.
Gate travel source/arrival is only a hint; validate against Land-local key adjacency/shared Gate helpers or use normal spawn; not proof of previous travel.
A player agent holds at most ONE active session across all Lands: entering any Land (or a Gate travel) first closes the current session (game WS, SESSION_CLOSE, ROUTE_CLOSE) and only then opens the new route; if the new entry is denied or fails, the old session stays closed. Enforced in the agent for its own key; a Land cannot see other Lands' sessions, so a second agent or copied key is not prevented (Land-side per-key replacement in step 11 still applies). Position may survive Hub switch in Land RAM; Land restart returns to approved spawn.

## 12. Quests — phase 2 after the milestone

All limits per Hub; Sybils/multiple Hubs multiply quota. ## 18. Threat model

Assume malicious Hubs/Players/Lands, unlimited keys, replay/drop/modification/restarts. Trust endpoints, selected identity keys and local OS controls.

| Threat | Mitigation / residual weakness |
| --- | --- |
| Hub forges identity/admission | Sender signatures/intended recipient/context, NK card key; Hub replies cannot grant seats |
| Hub compromise / public source disclosure | Compromising the Hub leaks no Player/Land root seeds, wallet/identity private keys or Noise session keys: their key-holding code and keys are never in the Hub repo or deployed on the Hub. The Hub's own signing/TLS/deploy credentials can be compromised and must be replaced; they grant no Land admission. Public protocol specs/vectors reveal nothing secret: fixture seeds are synthetic, never live keys. Open source is not protection against compromised endpoints or malicious builds; public reproducible builds let users verify the agent they run |
| Hub reads/alters content | NK before signed entry, AEAD header/strict counters; endpoint compromise outside relay protection |
| Drive-by scheme launch / hostile discovery site | Strict bounded nonsecret enter URL, safe arguments/authenticated IPC, configured-Hub verification/high-water, mandatory native Enter/Cancel before entry/bootstrap, launch budget and one pending dialog; no admission privilege or web-readable result. Focus changes and OS launch prompts remain observable; website snapshots are untrusted discovery only |
| Link forwarded | Single-use bearer/expiry/revoke; first redeemer may be wrong person; owner removes membership; optional key binding later |
| Invite brute force/used-code replay | Random 256-bit code, mandatory expiry, IP/key/Land limits; same-key used-code retry idempotent only while still eligible; another key fails |
| Land key leak = name + population only | Card is nonsecret; exact lookup has IP/key limits and no enumeration endpoint; Land membership/bans enforce entry; cached public cards stay nonsecret after door change |
| Land forges profile/hostile display data | Player-signed profile in GREETING, original signature relayed, client key/revision checks; bounded escaped text and safe img-only decoding |
| Stale card replay/restart | Stale/replayed card never makes a Land look open; fresh per-Hub signed tunnel observation + route/entry check; persistent high-water/hash, durable revision, 10 min expiry, one refetch; withholding remains |
| Nonce memory/restart replay | Expiry+skew retention, reject capacity not evict, fresh boot/connection/session, monotonic timing |
| Copied proof/multi-Hub redemption race | Challenge+transcript signature, one agent atomic challenge store plus Node transaction, durable membership before seat |
| Old session/direct Colyseus bypass | Capability/exact reservation/generation, one key/session; loopback alone insufficient |
| Localhost attack/rebinding | Exact Host/Origin, bootstrap/capability/WS handle/ACL/CSP; no key-export/arbitrary-signing API; same-user malware/admin still wins |
| Compromised/buggy game Node vs agent | Fixed structured kinds only, agent retains keys/transcript checks; no arbitrary signing/key disclosure; Node still trusted for game/door decisions |
| Browser/local attacker vs Node local API | Loopback/exact Host, reject browser Origin, separate 32-byte token/owner ACL, bounded schemas/IDs; same-user malware/admin remains trusted |
| Agent crash/restart | Fresh Noise key/boot; discard sessions/challenges/seats, Node drops generations, commit higher card revision; no restoration; channel loss fails closed |
| flynn/noise supply chain | Exact version/commit/hash, suite/transcript vectors, evidence with unknown audit status explicit; updates require evidence review and all vectors/CI rerun |
| Card URL/forwarding SSRF | Approved origins/IP validation/no redirects; fixed local target/path allowlist |
| Slow reader/oversized/chunks | Preallocation/chunk deadlines/queues/fairness/route close; tunnel TCP head-of-line remains |
| Silent blocking/colluding Hubs | Encrypted ping/new session elsewhere; no availability when all paths block |
| Disk failure/older restore/duplicate Land | SQLite WAL/FULL transactions fail closed; matched Land recovery bundle, external epoch/publication bound and serving lock until explicit reconciliation/new identity (section 7), restore tests and identity lock; copied identity not solved by consensus |
| Clock lies/rollback | Bounded hint, signed lifetime, monotonic deadlines/retention; bad clock can deny service |
| Quest prompt injection/spam/fraud | Data-only input/rule-owner gate/quotas/blocklist; no global Sybil defense or guaranteed reward |
| Key theft/plain backup | Restricted files/export warnings/new-identity recovery; no v1 passphrase/remote revocation authority; one leaked Player root-seed file leaks both identity and wallet (no separate wallet compartment) |
| Covert/forced mining | Off by default; explicit consent screen and current in-mine state required; visible indicator/Stop; no unconsented or hidden background mining |
| Wallet key theft/malware | Root seed in the restricted key file, no local-API export, explicit-user CLI export/import; same-user malware/admin can still steal the seed (identity and wallet together); Land root seed (identity + reward wallet) lives only in the Land agent file; Node can only request fixed-type transfers capped per transaction and per UTC day (total debit including network/priority fees; a compromised Node can drain at most the daily cap per day, restore/import never refreshes that budget); the wallet address in GREETING is visible to the Land/Node but not the Hub |
| Miner abusing CPU | Enforced user CPU cap, visible usage/running state and immediate Stop; C3 tests cap under load |
| Fake "in mine" signal | Authenticate/bind local signal to current game session, reject stale/replayed state, stop on leave/loss; consent remains independent; compromised endpoint is residual risk |
| Chain reorg vs displayed gold | C4/C5 reconcile canonical balance/settlement, distinguish pending/stale from confirmed, fail closed on unavailable chain; no SQLite gold fallback |
| Local API abuse to drain wallet | Exact Host/Origin, capability/token, fixed-type sends with explicit destination/amount/fee approval and replay/idempotency checks; no arbitrary signing |
| Metadata correlation | Numeric telemetry/no content logs/<=72 h IP logs; Hub still sees keys/IPs/sizes/timing |
